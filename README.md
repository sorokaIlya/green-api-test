# MAX Чаты — GREEN-API

Веб-чат на React + TypeScript для отправки и получения **текстовых** сообщений в мессенджере MAX через [GREEN-API](https://green-api.com/v3/docs/).

## Сценарий

1. Пользователь открывает сайт и на экране входа вводит учётные данные GREEN-API: `idInstance` и `apiTokenInstance`. Экран чатов открывается, только если GREEN-API принял эти данные.
2. Нажимает «+», вводит номер телефона получателя и создаёт новый чат.
3. Пишет текстовое сообщение и отправляет его получателю в MAX.
4. Получатель отвечает в мессенджере MAX.
5. Ответ появляется в открытом чате (в остальных чатах — счётчик непрочитанных).

## Запуск

```bash
npm install
npm run dev
```

Учётные данные вводятся в интерфейсе. Для разработки их можно задать заранее: скопируйте `.env.example` в `.env` и заполните:

```env
VITE_GREEN_API_URL=https://api.green-api.com/
VITE_ID_INSTANCE=...
VITE_API_TOKEN_INSTANCE=...
```

Значения из `.env` только подставляются в форму входа — войти всё равно нужно кнопкой «Войти». Успешный вход запоминается в `localStorage`, после перезагрузки экран входа не показывается. Кнопка «Выйти» в левой панели сбрасывает учётные данные и локальную историю чатов.

Другие команды: `npm run build` (проверка типов и сборка), `npm run format` / `npm run format:check` (Prettier).

## Методы GREEN-API

| Шаг                               | Метод                                                      | Где вызывается               |
| --------------------------------- | ---------------------------------------------------------- | ---------------------------- |
| Включение получения уведомлений   | `setSettings` (`webhookUrl: ''`, `incomingWebhook: 'yes'`) | `AuthStore.signIn`           |
| Проверка номера при создании чата | `checkAccount` → `chatId`                                  | `ChatStore.resolveRecipient` |
| Отправка текста                   | `sendMessage` с `{ chatId, message }`                      | `ChatStore.sendText`         |
| Получение входящих                | `receiveNotification` + `deleteNotification`               | `ChatStore.pollLoop`         |

Номер нормализуется перед проверкой (только цифры, 11–15 знаков, ведущая `8` у российского номера заменяется на `7`). Если чат с этим номером уже есть, он просто открывается: повторный `checkAccount` не вызывается, чтобы не попасть под ограничения мессенджера за частые проверки.

Из входящих уведомлений обрабатываются только `incomingMessageReceived` с типом `textMessage`, остальные удаляются из очереди без отображения — по заданию нужны только текстовые сообщения.

`setSettings` очищает `webhookUrl` инстанса: пока он задан, `receiveNotification` не возвращает уведомления. Если у инстанса уже был настроен вебхук, он будет отключён.

Polling идёт, пока открыт экран чатов (long polling с `receiveTimeout: 5`). Остановка обрывает текущий запрос через `AbortController`. При ошибках задержка между запросами растёт экспоненциально до 30 с, а уведомление об ошибке показывается один раз за серию.

## Состояние

- API отделён от сторов: `GreenApiService` — обычный класс (не стор) с одним экземпляром axios. Он создаётся один раз в `RootStore` и берёт учётные данные у провайдера `() => authStore.credentials` в момент каждого запроса, поэтому после входа и выхода его не нужно пересоздавать. Сторы получают сервис через конструктор и не знают, где хранится токен.
- Три стора: `AuthStore` — сессия (учётные данные, вход, выход), `ChatStore` — чаты, сообщения и приём входящих, `ChatUiStore` — состояние интерфейса. `ChatStore` сообщает об ошибках в UI и узнаёт открытый чат через колбэки; `ChatUiStore` вычисляет открытый чат (`activeChat`) из данных `ChatStore`. `RootStore` — composition root: конструктор только создаёт зависимости и связывает их, без побочных эффектов; восстановление состояния — в `init()`. Синглтона нет: `StoresProvider` создаёт `RootStore` для своего дерева компонентов (на сервере был бы свой на каждый запрос), вызывает `init()` в эффекте, то есть только в браузере, и показывает приложение после его завершения. Пока `init()` не завершился, показывается `fallback` — `Loader`, который становится видимым только через 200 мс: на localStorage восстановление занимает миллисекунды и лоадер не мигает, а на медленном хранилище появляется спиннер. В тестах в провайдер можно передать свой `RootStore`. Компоненты получают сторы через `useStores()` и подписываются через `observer`.
- Производные значения — `isAuthorized`, `activeChat` — вычисляемые (`computed`), а не синхронизируются вручную. Данные меняются мутациями внутри actions, как принято в MobX.
- Приём входящих запускает `ChatWorkspace` при монтировании (`startPolling`) и останавливает при размонтировании (`stopPolling`). Экран чатов появляется только после восстановления данных и входа, поэтому отдельных флагов и ожиданий в сторе нет. Цикл опроса привязан к `AbortController`: остановка отменяет и паузу, и висящий запрос, а двойной mount в StrictMode безопасен.
- Сохранение состояния разделено на три части:
  - **что сохранять** — стор реализует контракт `Persistable` и объявляет `persistOptions` (ключ и поля, имена полей проверяются через `keyof`): `AuthStore` — `credentials` под ключом `Auth`, `ChatStore` — `chats` под ключом `Chats`; UI-состояние не сохраняется;
  - **где хранить** — `StorageAdapter`, передаётся в `RootStore` снаружи: `localStorage` в браузере, память в тестах и вне браузера; подойдёт и асинхронное хранилище;
  - **как** — `Persister`: `restore(store)` завершается, когда данные восстановлены в стор и дальше сохраняются. Сторы не знают ни про `mobx-persist-store`, ни про `window`, поэтому библиотеку или хранилище можно заменить, не трогая их.
- Учётные данные попадают в `authStore.credentials` только после успешного `setSettings`, поэтому вошёл ли пользователь — это просто `credentials !== null` (`isAuthorized`). Поля формы входа хранятся в `uiStore.credentialsDraft` и попадают в `AuthStore` только по «Войти». Выход (`signOut`) по очереди останавливает приём и очищает чаты, удаляет учётные данные и сбрасывает UI.
- У чата два идентификатора: `id` — локальный ключ приложения (`chat-79991234567`), `remoteChatId` — идентификатор чата на стороне провайдера (`chatId` из `checkAccount`, например `79991234567@c.us`). Методы стора, работающие с чатами внутри приложения, принимают `id`; отправка и входящие сообщения используют `remoteChatId`.
- Use-cases (`signIn`, `signOut`, `createChatByPhone`, `sendTextMessage`) устроены одинаково: принимают нужные сторы, берут ввод из `uiStore` и оркестрируют сценарий, а API-вызовы остаются внутри сторов.
- Через props передаются только визуальные параметры чистых компонентов (`Avatar`, `Icon`). Бизнес-состояние компоненты берут из стора.

## Ограничения прототипа

- `apiTokenInstance` хранится в `localStorage` браузера. В production токен лучше держать на сервере-прокси.
- История сообщений не загружается с сервера: в чате видны сообщения, отправленные и полученные в этом браузере.
- Входящие сообщения от номеров, для которых не создан чат, не отображаются.
